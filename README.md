### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут добавлять/удалять датчики, устанавливать статуы и значение на датчике, менять параметры датчика, такие как: Location, Name, Type и тд..
- Так же можно менять статус датчика. Можно ли поставить on/off из реализации не ясно.

**Мониторинг температуры:**

- Пользователи могут получать все датчики и их значения, получать значения с конкретного датчика по его ID или Location


### 2. Анализ архитектуры монолитного приложения

- Язык Go
- DB PostgreSQL
- Монолит, весь спектр реализованых задач в рамках одного приложения. Для развёртывания нужно останавливать приложение целиком.
- Взаимодействие синхронное

### 3. Определение доменов и границы контекстов

- Домен управления датчиками
- Поддержка: подключение новых устройств
- Личный кабинет пользователя
- Хранение данных

### **4. Проблемы монолитного решения**

- Логика по управлению датчиками и логика мониторинга температуры связаны. Изменения в логике чтения показаний потребует остановки приложения
- Нет возможности добавлять другие устройства
- Потоки данных от устройств и пользователей делят одну базу
- Все вызовы синхронны, очередей нет. В пик нагрузка может привести в увеличению отклика всей системы, что можен негативно сказаться на надёжности
- Сложности с маштабирование. Тут можно либо масштабировать всю систему целиком или писать дополнительные компоненты для работы с базой, очередями.
- Добавить произвольный датчик пользователь не может.
- Датчик не умеет сам общаться с системой
